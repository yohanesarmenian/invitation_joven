# Open Questions

Only material unresolved questions that affect product, architecture, database, API, UI behavior, or implementation gates are listed here. Do not fill these gaps by assumption during implementation.

Resolved by Phase 0D and no longer open:

- Known spouse representation: normal named Invitee.
- Known child representation: normal named Invitee.
- Optional unnamed adult companion: `PLUS_ONE`.
- Optional unnamed/additional children: `ADDITIONAL_CHILD`.
- `Invitation.max_additional_children` applies only to unnamed/additional children.
- Attendance source-of-truth separation: `InvitationEvent`, `RSVPEventSelection`, `RSVPAttendee`, and `CheckinRecord`.
- Public invitation/check-in credential redisplay: deterministic server derivation.
- Check-in uniqueness: confirmed attendance is unique by `Invitation + Event`.
- Archive behavior: public/RSVP/message/check-in denied; OWNER history retained.

## Resolved by Phase 5 Slice 5B0

Owner decisions locked for Phase 5. These are now authoritative; do not re-litigate them during implementation.

- RSVP cutoff value — Decision: cutoff is `25 December 2026, 23:59:59 Asia/Jakarta (WIB, UTC+7)`, equivalent instant `2026-12-25T16:59:59Z`, held in the persisted `Invitation.rsvpDeadlineAt`. Date/phase: 2026-09-29, Phase 5 Slice 5B0. Consequence: the Figma deadline value `25 December 2027` is Figma-stale and superseded; it must not be treated as application truth. The displayed wedding date `09 January 2027` is unchanged, and the cutoff now precedes it, so no chronological inconsistency remains. Phase 4 public copy needs no change.
- Public create/update cutoff behavior — Decision: public RSVP create and update are both allowed up to and including the cutoff instant and both rejected afterwards with `422 RSVP_DEADLINE_PASSED`. Public invitation GET remains available after the cutoff. Date/phase: 2026-09-29, Phase 5 Slice 5B0. Consequence: Phase 4's read-only behavior is unaffected; Phase 5 must enforce the cutoff in the RSVP transaction before applying state.
- OWNER post-deadline override — Decision: not defined or implemented in Phase 5, and no public override behavior may be invented. Date/phase: 2026-09-29, Phase 5 Slice 5B0. Consequence: any future OWNER override must be a separate authenticated admin contract.
- First-mutation `expectedVersion` — Decision: `expectedVersion` is `integer | null`. `null` is create-only and conflicts if an RSVP row exists at lock time; an existing RSVP requires the exact persisted `version`, otherwise `409 RSVP_VERSION_CONFLICT`. Initial persisted `version = 1`; each successful mutation increments it. Date/phase: 2026-09-29, Phase 5 Slice 5B0. Consequence: RSVP rows are created lazily; no empty/`PENDING` row is pre-created to manufacture a version.
- Accepted-event minimum — Decision: an `ACCEPTED` RSVP must select at least one eligible attending event. Zero attending events returns `422 EVENT_NOT_SELECTED`; no new error code is introduced. Date/phase: 2026-09-29, Phase 5 Slice 5B0. Consequence: the existing event-selection error code now explicitly covers the zero-event case.
- Dietary semantics — Decision: `RSVP.dietaryNotes` is household-level, optional, trimmed, maximum 500 characters after trimming, empty-after-trim becomes `null`, and is cleared to `null` on decline. Date/phase: 2026-09-29, Phase 5 Slice 5B0. Consequence: the 500-character maximum is documented consistently in the API and UI contract areas.
- Phase 5 vs Phase 6 pass boundary — Decision: Phase 5 implements only the minimal `CheckinPass` data lifecycle required for RSVP transactional consistency (accepted holds exactly one active pass, decline revokes, re-accept issues a new pass). Phase 6 owns QR rendering, QR presentation, the QR-centric confirmation UX, and later pass/check-in presentation. Date/phase: 2026-09-29, Phase 5 Slice 5B0. Consequence: Phase 5 is not a QR implementation and must not ship QR UI.

Guest check-in pass / QR contract decisions for Phase 6. These are now authoritative; do not re-litigate them during Phase 6 implementation.

Consequence: no schema or storage change is needed for QR display, because the credential is deterministically re-derivable; no credential-bearing public route is introduced; the lexical format is not the security boundary and server-side validation remains authoritative.

It reuses the current Phase 5E declined confirmation: the existing notice is shown, no QR is rendered, and no pass credential or pass metadata is displayed. Guests may still edit their response before the deadline under the existing RSVP rules. Date/phase: 2026-09-30, Phase 6 Slice 6B0. Consequence: the declined confirmation copy remains whatever the implementation defines (`apps/invitation-web/src/rsvp/notice.ts`), and final copy polish stays a separate copy decision rather than being invented during pass work.
- Guest pass presentation surface (D5) — Decision: the guest QR/pass is presented **inline within the existing public RSVP/result surface** on the invitation long page. Phase 6 introduces no dedicated pass route, no `/c/...` route, no separate guest portal, and no navigation to another public page. The Figma `Registered` state is a visual reference, not a routing requirement. Date/phase: 2026-09-30, Phase 6 Slice 6B0. Consequence: any later focused presentation state must still be hosted inside the existing invitation flow unless a future contract explicitly changes routing.

## Resolved by Phase 7 Slice 7B0

Guest message contract decisions for Phase 7. These are now authoritative; do not re-litigate them during Phase 7 implementation.

- **D1 — Retry / idempotency / duplicate semantics** — Decision: guest messages are **create-only append** operations. Every explicit successful submission creates a new `GuestMessage` row, and multiple messages from the same invitation are allowed. There is no idempotency key, no unique message-per-invitation rule, no optimistic version, no update-on-duplicate behavior, and no automatic retry. The frontend disables submit while a submission is pending and must not automatically retry the `POST` when the network outcome is uncertain. A guest may explicitly submit again; an explicit second submission is a new message and may duplicate if the earlier uncertain request actually committed. Date/phase: 2026-09-30, Phase 7 Slice 7B0. Consequence: **no schema change and no migration** — no idempotency column and no unique constraint are added. This closes the previously open "Guest message retry/idempotency" question.
- **D2 — Message content contract** — Decision: `message` is required, plain text only, trimmed of leading and trailing whitespace before persistence, rejected if empty after trimming, and limited to a maximum of **1000 Unicode characters after trimming**. Internal line breaks are preserved; Unicode and emoji are allowed. HTML is not interpreted, Markdown is not interpreted, links are not auto-converted to HTML, and the value must never be rendered with `dangerouslySetInnerHTML`. The stored value is the trimmed plain-text message, and rendering layers rely on normal text escaping. No HTML sanitizer dependency is added, because rich text is not part of the contract. Date/phase: 2026-09-30, Phase 7 Slice 7B0. Consequence: length and trimming are enforced at the DTO/application boundary; no database `CHECK` constraint is required for the MVP, and the previously deferred "length limits to be set during implementation" is now resolved.
- **D3 — Submission window** — Decision: guest message submission is **independent of RSVP existence, RSVP status, and `rsvpDeadlineAt`**. A message may be submitted whenever `Invitation.status` is `ACTIVE`, including when no RSVP exists, the RSVP is `ACCEPTED` or `DECLINED`, or the RSVP cutoff has passed. Submission is denied when the invitation is `ARCHIVED` or otherwise unavailable through the public credential boundary. Date/phase: 2026-09-30, Phase 7 Slice 7B0. Consequence: no `MESSAGE_DEADLINE_PASSED` code is introduced and `RSVP_DEADLINE_PASSED` is never reused for guest messages. The RSVP cutoff closes RSVP create/update only.
- **D4 — Author identity** — Decision: `authorName` is **optional guest-entered free text**. It is trimmed, empty after trimming becomes `null`, and the maximum length after trimming is **100 Unicode characters**. Unicode and emoji are allowed; content is plain text only. It is never derived from `Invitee`, `Invitation.greetingName`, or `RSVP`. Anonymous submission (`authorName: null`) is valid, and `GuestMessage` carries no public identity or account semantics. Date/phase: 2026-09-30, Phase 7 Slice 7B0. Consequence: no `inviteeId`, no author household id, and no account linkage are added; the existing nullable `author_name` column is already sufficient.
- **D5 — Public CRUD and response shape** — Decision: the Phase 7 public guest-message API is **create-only**: `POST /api/public/invitations/{publicCredential}/messages`. There is no public message list, no get-by-id, no update, no delete, and no public message wall. **`GuestMessage.id` is internal and is never returned publicly.** The public success response is `201 Created` with `{ "message": { "createdAt": "<ISO-8601>" } }` only. Date/phase: 2026-09-30, Phase 7 Slice 7B0. Consequence: this deliberately changes the earlier draft response, which returned `message.id`; the public client has no functional need for the row id, so an internal UUID is not exposed merely because it exists. Admin read and moderation remain Phase 8+.
- **D6 — Error contract** — Decision: **no new `MESSAGE_*` domain error codes** are introduced. Invalid request content returns the existing `400 VALIDATION_ERROR` envelope; unknown credentials, unavailable invitations, and archived invitations return the existing generic `404 INVITATION_NOT_AVAILABLE` without revealing which case occurred; unexpected failures use the existing generic server-error behavior. Error responses never echo message content, `authorName`, the public credential, or database IDs. Date/phase: 2026-09-30, Phase 7 Slice 7B0. Consequence: no new error envelope and no message-specific error code. Admin listing pagination, sort order, detail, and hide/unhide are **not** Phase 7 blockers and remain open for Phase 8+; no admin sort order is locked here.
- **D7 — Abuse / rate-limit posture** — Decision: Phase 7 introduces **no** CAPTCHA, Turnstile, Redis, Nest throttler, application rate-limit dependency, or new edge/proxy infrastructure. Mitigation is intentionally limited to the bearer public invitation credential, the `ACTIVE` invitation requirement, the 1000-character message cap, the 100-character `authorName` cap, strict DTO validation, submit-disabled-while-pending, no automatic `POST` retry, the generic unavailable response, and invitation-scoped writes. Repeated deliberate submissions remain possible; this is an **accepted MVP limitation**. Date/phase: 2026-09-30, Phase 7 Slice 7B0. Consequence: deployment/edge-level rate limiting is recommended before production exposure if abuse becomes a concern, and Phase 7 does not depend on infrastructure that does not exist in this repository.

## Resolved by Phase 8 Slice 8B0

Admin authentication and security contract decisions. These are now authoritative; do not re-litigate them during Phase 8 implementation. Documentation lives in `TECHNICAL-ARCHITECTURE.md` ("Admin Authentication Architecture"), `API-CONTRACT.md` ("Admin Authentication Endpoints", "Admin CSRF and origin doctrine"), and `DATABASE-SCHEMA.md` (`AdminUser`, `AdminSession`).

- **D1 — Production admin/API topology and cookie contract** — Decision: the MVP administration surface is **same-origin in the browser** (`https://<admin-host>/` plus `https://<admin-host>/api/**`). The public invitation site may live on another origin; the admin cookie is host-only and is never scoped to a shared parent domain. No cross-origin credentialed CORS for the MVP, no `Access-Control-Allow-Origin: *`, and no browser `credentials: "include"` across origins. Nest may run internally on another port/container behind a reverse proxy or development proxy. Production cookie: `__Host-admin_session`, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, `Domain` omitted, lifetime matching the session absolute expiration. Development/isolated-test only: `admin_session`, `HttpOnly`, `Secure=false`, `SameSite=Strict`, `Path=/`, no `Domain`; production must refuse to issue the insecure development configuration. Admin authentication requires HTTPS. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: this closes the previously open "Final admin auth deployment topology" question.
- **D2 — First OWNER bootstrap** — Decision: first-OWNER creation is **operator-only** through a CLI, conceptually `pnpm --filter api admin:bootstrap-owner`, reading `ADMIN_BOOTSTRAP_EMAIL` and `ADMIN_BOOTSTRAP_PASSWORD` from the runtime environment. There is **no** network bootstrap endpoint, no `/setup`, `/register`, or `/bootstrap` route, and no public admin registration. The values must never be committed, written to files by the command, logged, included in exception text, or persisted in plaintext. The command validates, normalizes the email, hashes with the locked Argon2id parameters, enters an atomic database critical section, verifies `admin_users` is empty, creates exactly one `ACTIVE` OWNER, and exits. If **any** `AdminUser` exists, it refuses and must not update the existing account, reset its password, create a second OWNER, or silently succeed. No default email, no default password, no hard-coded credentials. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: this closes the previously open "First admin OWNER bootstrap" question. **No schema change is required.**
- **D12 — Bootstrap concurrency and OWNER count doctrine** — Decision: the empty-table check and OWNER creation are concurrency-safe via a PostgreSQL transaction-scoped serialization mechanism (a transaction advisory lock or equivalent). Two simultaneous bootstrap commands produce exactly one successful creation and one safe refusal; a bare `SELECT count(*)` then `INSERT` is insufficient. The supported MVP deployment has **one effective OWNER**; the schema may structurally permit multiple rows, but Phase 8 adds no workflow to create additional OWNERs, no admin-user creation UI, no role management, and no `ADMIN`/`EDITOR`/`VIEWER` roles. **No database singleton constraint is added.** Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: closes the bootstrap-race and OWNER-invariant gaps together; no migration.
- **D3 — Admin login identity and password policy** — Decision: the login identifier is `email`, normalized by trimming outer whitespace then lowercasing, maximum 254 characters, syntactically valid; every supported `AdminUser` writer uses the same normalization. Password policy for the MVP without MFA: minimum **15** Unicode code points, maximum **128** Unicode code points, **not trimmed**, whitespace valid, Unicode allowed, no mandatory character-class rules, no silent truncation. The bootstrap password obeys the same policy. Hashing is **Argon2id** via **`@node-rs/argon2`** with `memoryCost = 19456` KiB, `timeCost = 2`, `parallelism = 1`, and a library-generated random salt; only the encoded hash is persisted. `bcrypt`, `bcryptjs`, SHA-256, HMAC, and PBKDF2 are not used for password storage. No pepper is required. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: the algorithm was already documented; the dependency, parameters, policy, and normalization are now locked. Phase 8 adds no password strength library, breached-password lookup, email reset, password-change UI, or MFA.
- **D4 — Session token, lifetime, activity, and rotation** — Decision: opaque random sessions, **not JWT**. Each login uses **32 cryptographically secure random bytes** from Node cryptographic randomness, encoded as unpadded Base64URL (conceptually 43 characters); a new token is created on every successful login and a client-supplied session identifier is never accepted. Only `SHA-256(sessionToken)` is persisted, in `AdminSession.sessionTokenHash`; the raw token exists only transiently and in the `HttpOnly` cookie. Absolute lifetime **12 hours** from login, fixed at `expiresAt` and never extended; idle timeout **30 minutes** evaluated against `lastSeenAt` when present, otherwise `createdAt`. A session is valid only when the `AdminUser` is `ACTIVE`, `revokedAt IS NULL`, `expiresAt > now`, and the idle window has not elapsed. `lastSeenAt` is written only when at least approximately 5 minutes have elapsed since the stored activity timestamp, never on every request. **No mid-session token rotation**, and expired sessions are never reactivated. Expired/revoked rows are immediately unusable while present; bounded opportunistic cleanup may delete rows older than a recommended **7 days** past expiry or revocation, with no cron, scheduler dependency, or background worker added for it. `userAgent` and `ipAddress` stay `null` in the MVP — no proxy-trust configuration, fingerprinting, geolocation logic, or PII retention is introduced merely because the nullable columns exist. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: closes the session-lifetime, idle-timeout, rotation, cleanup, and telemetry gaps; no schema change.
- **D5 — CSRF model and origin protection** — Decision: every authenticated unsafe admin operation (`POST`, `PUT`, `PATCH`, `DELETE`) requires the `X-CSRF-Token` header, with the single exception of `POST /api/admin/auth/login`. `GET`/`HEAD`/`OPTIONS` must not mutate state and require no token; logout remains CSRF-protected. One deterministic CSRF token is bound to each `AdminSession`: `HMAC-SHA256(key = raw session token bytes, message = "admin-csrf-v1")`, encoded as unpadded Base64URL, with only `SHA-256(csrfToken)` persisted in `AdminSession.csrfTokenHash`; comparison is timing-safe. Because the token is derivable from the raw session token, the API re-derives it at session bootstrap without persisting the raw token. A successful login **and** `GET /api/admin/auth/me` both return the raw token, which is the recovery path after a refresh or a new server render; the token lasts only for that session's lifetime. No double-submit cookie, no CSRF token in a URL, no CSRF token in `localStorage`/`sessionStorage`. Defense in depth: all browser unsafe admin requests, **including login**, must pass exact `ADMIN_ORIGIN` validation — `Origin` exact-match when present, otherwise `Referer` origin exact-match, otherwise reject; no substring or suffix matching. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: the previously unspecified CSRF mechanism is now locked; broad CORS is explicitly not the answer.
- **D6 — Auth error contract and response shapes** — Decision: `400 VALIDATION_ERROR` for malformed auth bodies; `401 INVALID_CREDENTIALS` for login failure covering unknown email, wrong password, and `DISABLED` accounts indistinguishably; `429 TOO_MANY_LOGIN_ATTEMPTS` when the login throttle rejects; `401 UNAUTHENTICATED` for missing cookie, malformed token, unknown session, expired session, idle-expired session, revoked session, and a session whose `AdminUser` is `DISABLED`; `403 FORBIDDEN` for an authenticated session without the required role; `403 CSRF_INVALID` for missing, invalid, or session-mismatched CSRF tokens and for failed admin-origin validation, without disclosing which check failed. **No public `SESSION_EXPIRED` code** — one generic `UNAUTHENTICATED` keeps the admin client to a single state. Login returns `200` with `{ user: { id, email, role }, session: { expiresAt }, csrfToken }`, updates `AdminUser.lastLoginAt`, and creates the session; the raw session token is never in the body. `GET /api/admin/auth/me` returns the same shape and never returns a session id, session token, `sessionTokenHash`, `csrfTokenHash`, `passwordHash`, `ipAddress`, or `userAgent`. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: closes the error-code and `me`-shape gaps that blocked admin-web; Phase 10B makes `FORBIDDEN` observable for CHECKIN_STAFF attempts against OWNER-only routes.
- **D7 — Login throttling and enumeration safety** — Decision: the API implements a small **in-process** login limiter — per normalized email, 10 failed attempts per 15 minutes; process-wide, 100 failed attempts per 15 minutes; unknown emails participate in the same per-email limiter; a successful login clears the email's bucket; on threshold, `429 TOO_MANY_LOGIN_ATTEMPTS` without indicating whether the account exists. No Redis, no database attempt counter, no lockout column, no CAPTCHA, and no new rate-limit infrastructure. Limiter state is intentionally ephemeral, resets on process restart, and is not an account status in `AdminUser`. Unknown email, wrong password, and `DISABLED` all produce the same `401 INVALID_CREDENTIALS`; where needed to avoid materially distinguishable password-verification timing, an application-owned dummy Argon2id hash is used on the no-user path. No schema change and no migration. This is acceptable **only** for a single-API-instance deployment; before horizontal scaling, move throttling to a shared edge or store mechanism. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: this deliberately does **not** carry Phase 7's accepted no-rate-limit posture into admin password login.
- **D8 — Admin Guest Message ownership** — Decision: admin guest-message visibility and moderation **is owned by Phase 8**, resolving the roadmap conflict between the ownership sentence and the Phase 8 task list. It is **not** part of the auth-foundation slices 8B and 8C and requires its own admin-domain contract lock (Slice 8D0) before implementation. Phase 8 is therefore not complete once auth and the admin shell ship. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: the ownership sentence in `IMPLEMENTATION-ROADMAP.md` is now consistent with the slice plan. Listing pagination, sort order, detail, field selection, `authorName` handling, and hide/unhide request/response semantics remain open and move to 8D0. No schema change is expected.
- **D9 — Authorization doctrine and admin-web integration** — Decision: the **backend** is the authoritative security boundary; admin-web route protection is UX and defense in depth. Every `/api/admin/**` operation except login independently enforces a valid session, OWNER authorization where required, and CSRF plus origin validation for unsafe methods; client route state, hidden UI, a Next layout, or browser-side role data are never treated as authorization. admin-web uses **server-side session bootstrap** for protected layouts, calling `GET /api/admin/auth/me` before rendering and redirecting unauthenticated visitors to `/login`; **no Next `middleware.ts` is required for the MVP**. admin-web declares `@wedding-invitation/api-client` as a proper workspace dependency and does not introduce new `../../packages/api-client/src/**` relative-source imports. Browser-facing admin requests use the same-origin `/api` surface; server-side admin-web requests may use an internal API base URL but must forward only the required session cookie and must not forward arbitrary browser headers. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: closes the route-protection-mechanism and API-client-integration gaps. Exact guard and decorator class names remain an implementation choice, not a contract.
- **D10 — Multiple sessions** — Decision: multiple simultaneous sessions per OWNER are **allowed**. A successful login does not revoke other valid sessions. There is no one-session-per-OWNER constraint, no revoke-other-sessions-on-login behaviour, and no "sign out everywhere" operation in the Phase 8 auth foundation. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: the existing schema already supports this; no change.
- **D11 — Session expiry UX** — Decision: when `/me` or any protected admin API call returns `401 UNAUTHENTICATED`, admin-web returns the user to `/login` with one concise generic state — "Your admin session has ended. Please sign in again." — without distinguishing expired, revoked, disabled, or missing sessions. Sensitive form drafts are **not** persisted to browser storage merely to survive session expiry. After a successful login, navigate to the admin dashboard; there is no re-auth modal in the MVP. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: closes the session-expiry UX gap. The concrete login-screen visual design remains open for Slice 8C.
- **D13 — Logout scope** — Decision: `POST /api/admin/auth/logout` revokes the **current session only** — it sets `revokedAt` on the current `AdminSession`, clears the current cookie using the same name, path, and environment configuration used at login, and returns `204`. Other OWNER sessions are unaffected. A future "logout everywhere" capability is outside the Phase 8 auth foundation. Date/phase: 2026-09-30, Phase 8 Slice 8B0. Consequence: closes the logout-scope ambiguity in the API contract.

Auth-foundation implementation blockers D1-D13 are now **resolved**. Later admin-management questions — including the admin-management surface itself, Guest Message listing/moderation details, and invitation-link regeneration retry/idempotency — were carried forward to **Slice 8D0** and were not auth blockers. **Slice 8D0 then resolved them**; see the next section.

## Resolved by Phase 8 Slice 8D0

Admin-management contract decisions. These are now authoritative; do not re-litigate them during Phase 8 implementation. Documentation lives in `API-CONTRACT.md` ("Admin Management Conventions", "Admin Dashboard", "Admin Invitation Endpoints", "Admin Invitee Endpoints", "Admin Event Endpoints", "Admin RSVP Endpoints", "Admin Message Endpoints", "Admin Response Privacy"), `TECHNICAL-ARCHITECTURE.md` ("Admin Management Architecture"), `DATABASE-SCHEMA.md` ("Phase 8 Admin Management"), `UI-UX-SPEC.md` ("Admin Management UI Contract"), and `DEVELOPMENT-RULES.md`.

- **D1 — Shared admin pagination** — Decision: one envelope for every admin list, `{ items, page: { number, pageSize, totalItems, totalPages } }`; `page` is 1-based, default `1`, minimum `1`; `pageSize` defaults to `25`, maximum `100`; invalid values return `400 VALIDATION_ERROR`; `totalItems` counts rows after filters and before pagination; `totalPages = ceil(totalItems / pageSize)` with `0` for zero items; a page beyond the last returns empty items with the requested number and correct totals, and is not a `404`; no cursor pagination in Phase 8. Consequence: three admin lists depend on one shape, so the shape is locked once. No schema change.
- **D2 — Shared sorting** — Decision: `sortBy` plus `sortOrder` (`asc` | `desc`), whitelisted per endpoint, `400 VALIDATION_ERROR` on an unsupported value, and `id ASC` appended as a deterministic final tie-breaker on every ordering. Defaults: invitations `createdAt DESC`, RSVPs `updatedAt DESC`, guest messages `createdAt DESC`, events `displayOrder ASC`. Never sortable: credential, `publicTokenHash`, `publicTokenVersion`, `Invitation.notes`, `GuestMessage.message`, auth/session fields. Consequence: page boundaries stay stable; no schema change.
- **D3 — Search** — Decision: trim, treat empty-after-trim as omitted, cap at 100 Unicode code points, case-insensitive partial match, no full-text/trigram extension and no new index. Invitation search covers `Invitation.displayName`, `Invitation.greetingName`, and `Invitee.fullName`; RSVP admin search covers the same fields through the related invitation; guest messages have **no** free-text body search in Phase 8. Never searchable: the public credential, `publicTokenHash`, `publicTokenVersion`, internal UUIDs, `CheckinPass` credential or hash, and auth/session fields. No schema change.
- **D4 — Admin error doctrine** — Decision: `400 VALIDATION_ERROR` for malformed input, `404 NOT_FOUND` for a missing admin resource, `409 CONFLICT` for admin state/concurrency conflicts with no more-specific code. Existing RSVP domain codes stay authoritative where they apply. The public `404 INVITATION_NOT_AVAILABLE` is **not** reused for authenticated admin lookups, because its public-indistinguishability purpose does not apply behind OWNER auth. Consequence: two codes are added to `API-CONTRACT.md`; no schema change.
- **D5 — Phase 8 dashboard** — Decision: the dashboard ships only `invitations.{active,archived,openedActive}`, `rsvp.{pending,accepted,declined}`, and `expectedByEvent[].{event,expectedAttendeeCount}`. `pending` counts active invitations with no RSVP row **or** with `RSVP.status = PENDING`. Archived invitations are excluded from all RSVP and headcount metrics. The earlier sample's `checkin` block, `headcount.expectedTotal`, adult/child totals, and reporting charts are **removed from Phase 8**: `CheckinRecord` has no writer until Phase 10, and a cross-event total double-counts multi-event households. Consequence: the illustrative payload was replaced; no schema change.
- **D6 — Invitation list** — Decision: filters `status`, `rsvpStatus` (where `PENDING` includes the no-RSVP case), and `search`; item fields `id`, `displayName`, `greetingName`, `status`, `rsvpStatus`, `inviteeCount`, `openCount`, `lastOpenedAt`, `rsvpDeadlineAt`, `createdAt`, `updatedAt`, `archivedAt`. The item excludes the public credential, public URL, `publicTokenHash`, `publicTokenVersion`, `notes`, invitee arrays, messages, `qrPayload`, pass credentials, and any guest-message count. No schema change.
- **D7 — Invitation detail** — Decision: detail returns the invitation fields — including `notes` and `publicTokenVersion`, both of which the list item deliberately omits — plus embedded invitees, eligibility with safe event metadata, an RSVP summary, a message count summary (`total`, `hidden`), and check-in pass **metadata** history. It deliberately excludes the raw public credential, public URL, `qrPayload`, `CheckinPass.tokenHash`, auth/session fields, and `CheckinRecord` history. The public URL is fetched only from the explicit `public-url` endpoint, keeping credential material out of normal detail responses. Consequence: the earlier "current public URL if the backend chooses to include it" wording is gone, and the previously documented CheckinRecord history is deferred to Phase 10. No schema change.
- **D8 — Invitation create** — Decision: one request creates the Invitation, `InvitationEvent` rows, and invitees in **one transaction**; invitees receive `displayOrder` from request array position; duplicate invitee names are allowed; `eventIds` must be duplicate-free and must reference existing selectable events; the invitation starts `ACTIVE` at `public_token_version = 1`; the credential is derived through the existing deterministic derivation and only the hash is stored; no RSVP row is created. Create is **not idempotent**: no idempotency key, no content dedup, and admin-web never auto-retries after an uncertain result — it reloads the list and lets the OWNER decide. No schema change.
- **D9 — Invitation update** — Decision: writable fields are `displayName`, `greetingName`, `allowPlusOne`, `maxAdditionalChildren`, `rsvpDeadlineAt`, `notes`. `status`, `archivedAt`, `publicTokenVersion`, `publicTokenHash`, the open aggregates, invitees, eligibility, and RSVP are not writable here. Concurrency uses **`expectedUpdatedAt`** compared under the Invitation row lock, returning `409 CONFLICT` with no writes on mismatch. No silent last-writer-wins. **No `Invitation.version` column is added**; `RSVP.version` is unchanged and separate. No schema change.
- **D10 — Archive** — Decision: archive takes no payload; the illustrative `reason` property is **removed**, because there is no `archiveReason` column and the contract does not accept data it cannot persist. Archive sets `status = ARCHIVED` and `archivedAt` under the row lock, preserves every child and history row, does not rotate the credential, and does not mutate RSVP/pass/message history. Archive is **idempotent** and returns the existing `archivedAt` unchanged. **No unarchive exists in Phase 8.** No schema change.
- **D11 — Public URL** — Decision: a new non-secret configuration value `PUBLIC_INVITATION_BASE_URL` supplies the guest-facing origin; it must be an absolute origin with no path, query, fragment, or credential, must be HTTPS in production, and must never be derived from a request header. Only an `ACTIVE` invitation returns a usable URL; an archived invitation returns `409 CONFLICT`. The endpoint re-derives the credential, verifies it against the persisted hash, never silently repairs a mismatch, **does not touch `openCount`/`firstOpenedAt`/`lastOpenedAt`**, never persists plaintext, and is never deliberately logged. Consequence: `.env.example` gains one non-secret placeholder; no schema change.
- **D12 — Token regeneration retry/idempotency** — Decision: the request requires **`expectedTokenVersion`**. The transaction locks the Invitation row, requires `ACTIVE`, compares the persisted `publicTokenVersion`, returns `409 CONFLICT` with no rotation on mismatch, then increments the version and replaces the hash together. Regeneration is **not** automatically retryable; admin-web keeps one pending request and treats an uncertain outcome as unknown. Recovery is a read of `GET /api/admin/invitations/{id}/public-url`, which re-derives the currently valid link because derivation is deterministic. An explicit retry with the old `expectedTokenVersion` returns `409 CONFLICT` and does not rotate again. **No `Idempotency-Key`, no idempotency table, no new column.** Consequence: this closes the "Invitation link regeneration retry/idempotency" question carried from Slice 8B0. No schema change.
- **D13 — Concurrent regeneration** — Decision: two requests carrying the same `expectedTokenVersion` serialize on the Invitation row lock; the first succeeds, the second observes the changed version and returns `409 CONFLICT` with no rotation, so exactly one version increment occurs per displayed state. There is no "both succeed, last writer wins" behavior. No schema change.
- **D14 — Invitee create/update** — Decision: create requires an `ACTIVE` invitation, trims and requires a non-empty `fullName`, trims `label` with blank normalized to `null`, accepts only the existing `ADULT`/`CHILD` categories, allows duplicate names, and assigns `displayOrder` under the Invitation row lock. Create is not idempotent and is never auto-retried. Update writes `fullName`, `category`, `label`, keeps `id`, `invitationId`, and `displayOrder` immutable, and requires `expectedUpdatedAt` with a `409 CONFLICT` on staleness. **Phase 8 implements no invitee reordering.** No schema change.
- **D15 — Invitee delete** — Decision: hard delete only. If any `RSVPAttendee` references the invitee, return `409 CONFLICT` and delete nothing; no implicit RSVP/attendee reconciliation is performed. Otherwise delete and return `204`, and also return `204` when the invitee is already absent so a lost successful response can be retried. **No soft-delete or inactive invitee state exists, and none is added.** Consequence: this closes the earlier "only if safe; otherwise use future inactive/archive behavior" wording, which left the safety condition unnamed. No schema change.
- **D16 — Post-RSVP invitee edits** — Decision: editing `Invitee.fullName`, `category`, or `label` never rewrites existing `RSVPAttendee` rows. Submitted RSVP composition is a snapshot; `RSVPAttendee.displayName` exists precisely to decouple the two. Correcting the RSVP itself is done through the OWNER override. No schema change.
- **D17 — Eligibility management** — Decision: one declarative `PUT /api/admin/invitations/{invitationId}/events` with `{ eventIds }`, set-to-value and therefore retry-safe, duplicate-free, requiring existing selectable events and an `ACTIVE` invitation, in one transaction under the shared Invitation row lock. Before removing any `InvitationEvent`, if **any** `RSVPEventSelection` references an event being removed, the **entire** replacement is rejected with `409 CONFLICT` and zero eligibility changes occur; selections are never deleted, rewritten, or orphaned. The documented workflow is to change the RSVP through the OWNER override first. `RSVPEventSelection` has no FK to `InvitationEvent`, so this application check is the only guard on the invariant. No schema change.
- **D18 — Event catalog** — Decision: Phase 8 manages `InvitationEvent` eligibility only. A read-only `GET /api/admin/events` returns `id`, `slug`, `name`, `isActive`, and `displayOrder`, ordered `displayOrder ASC, id ASC`, including inactive rows so historical eligibility stays representable. **No `Event` create, update, or delete endpoint exists**, and historical eligibility is not silently deleted because an event becomes inactive. No schema change.
- **D19 — RSVP admin list/detail** — Decision: the list returns only persisted RSVP rows — invitations with no RSVP row are never synthesized into it — with `id`, a safe invitation summary, `status`, `version`, `attendeeCount`, `attendingEventCount`, `createdAt`, `updatedAt`, and a `submittedByAdmin` boolean derived from `submittedByAdminUserId != null`. `attendeeCount` is `SUM(RSVPAttendee.quantity)`, not row count, and `attendingEventCount` counts only `RSVPEventSelection.attending = true` rows. Detail adds selections, attendees, `dietaryNotes`, `guestNote`, and admin submission metadata (`submittedByAdmin`, optional `adminUser`, optional `overrideReason`), with pass history limited to safe metadata. **`qrPayload` is not exposed**: it is bearer check-in material, and Phase 8 admin UI never renders or reissues guest QR credentials. No schema change.
- **D20 — OWNER RSVP override** — Decision: `PUT /api/admin/invitations/{invitationId}/rsvp` takes the canonical public RSVP fields plus mandatory `expectedVersion` and mandatory `overrideReason` (trimmed, non-empty, maximum 500 Unicode code points). It **may bypass `rsvpDeadlineAt`** — the explicit meaning of the privileged override, and the separate authenticated admin contract that Phase 5 anticipated — and it **must not bypass** the `ACTIVE` requirement, eligibility, attendee composition, capacity and plus-one rules, canonical transitions, `CheckinPass` lifecycle, or `expectedVersion` concurrency. It reuses the **same underlying RSVP lifecycle implementation**; `CheckinPass` semantics are not forked. Every OWNER success writes `submittedByAdminUserId` and `adminOverrideReason`. These fields describe the current RSVP state, so a later successful public RSVP mutation clears both fields; failed public mutations leave both unchanged. `guestNote` is not writable in Phase 8 and its value is preserved. Pass lifecycle is preserved exactly: accept→accept keeps the active pass, accept→decline revokes it, decline→accept issues a new pass, decline→decline leaves no active pass. Consequence: this closes the previously undecided OWNER post-deadline override, which Phase 5 explicitly left to a separate admin contract. No schema change.
- **D21 — Guest message lists** — Decision: the global list and the invitation-scoped list share one query contract, one item DTO, one page envelope, and one `hidden` filter (`all` | `visible` | `hidden`, default `all`). The item carries the invitation summary even on the scoped endpoint, so one generated type and one admin component serve both. There is no free-text message-body search. Default sort is `createdAt DESC` with `id ASC`. No schema change.
- **D22 — Message moderation** — Decision: `PATCH /api/admin/messages/{messageId}` writes `isHidden` only, set-to-value and idempotent, returning the updated shared item; a missing message returns `404 NOT_FOUND`. There is no delete, no reason, and no moderation comment. Phase 8 records **no** `hiddenAt`, `hiddenByAdminUserId`, or moderation timestamp — an explicit MVP limitation. `isHidden` has **no public guest-facing effect**, because no public message wall exists; it is an internal moderation state. No schema change.
- **D23 — Admin-web route and UI contract** — Decision: protected routes are `/`, `/invitations`, `/invitations/new`, `/invitations/[invitationId]`, `/invitations/[invitationId]/edit`, `/rsvps`, `/rsvps/[rsvpId]`, and `/messages`; there is no top-level invitee, event, check-in, import, or report route in Phase 8. Navigation exposes Dashboard, Invitations, RSVPs, and Messages plus OWNER identity and sign-out, with no disabled placeholder navigation for unshipped phases. Every screen defines loading, empty, error, and session-ended states. Archive, token regeneration, and invitee deletion require explicit confirmation, and the regeneration flow must state that previously distributed links stop working immediately and that the action cannot be undone; regeneration never auto-retries and recovers from an uncertain outcome by re-reading `public-url`. Archive offers no unarchive affordance. No schema change.
- **D24 — Shared admin enforcement** — Decision: session, OWNER, CSRF, and origin enforcement is **one shared backend surface** that recognizes method safety itself, rather than a manual per-controller call. Safe methods (`GET`, `HEAD`, `OPTIONS`) require no CSRF token; unsafe methods require session, OWNER, exact `ADMIN_ORIGIN`, and a valid `X-CSRF-Token`; login is the only exception. A **route-inventory security regression test** is mandatory: for every `/api/admin/**` route except login a missing session returns `401 UNAUTHENTICATED`, and for every unsafe admin route a missing/wrong CSRF token or bad origin returns `403 CSRF_INVALID`, with the test failing if a future unsafe route is added without inheriting the shared enforcement. Consequence: the Phase 8B0 doctrine already required this enforcement; what was missing is that it was applied by hand at each route, which is safe for three auth routes and unsafe for dozens. No schema change.

Admin-management implementation blockers D1-D24 are now **resolved**.

CSV/XLSX import contract decisions. These are now authoritative; do not re-litigate them during Phase 9 implementation. Documentation lives in `API-CONTRACT.md` ("Admin Import Endpoints"), `TECHNICAL-ARCHITECTURE.md` ("Import Architecture"), `DATABASE-SCHEMA.md` (`GuestImportPreview`, `GuestImportBatch`), `UI-UX-SPEC.md` ("Import UI Contract"), and `PRD.md` ("Guest import"). - **D1 — Create-only MVP** — Decision: Phase 9 import is **create-only**. It creates new `Invitation`, `Invitee`, and `InvitationEvent` rows and never updates, upserts, or merges an existing invitation, and never modifies `RSVP`, `RSVPAttendee`, `RSVPEventSelection`, `GuestMessage`, `CheckinPass`, or `CheckinRecord`. There is no import business key for update or upsert semantics. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: possible duplicates stay warnings, and an OWNER may acknowledge a warning and intentionally create a similarly named new invitation.
- **D2 — One source row is one household** — Decision: each CSV record or XLSX data row represents exactly one household, equal to one `Invitation`. The source row is the atomic preview-selection unit, so `includeRowNumbers` continues to mean source household row numbers and no household spans multiple spreadsheet rows. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: preview rows, warning acknowledgment, selection, and commit atomicity stay aligned with the documented API shape.
- **D3 — Template and header contract** — Decision: base columns in exact order are `displayName`, `greetingName`, `allowPlusOne`, `maxAdditionalChildren`, `rsvpDeadlineLocal`, `notes`, `invitees`, followed by zero or more `event:<slug>` eligibility columns. Matching is exact after removing an optional UTF-8 BOM from the first header; there are no aliases and no silent rename of a misspelled header. Backend-owned fields are never accepted from a spreadsheet, and `Event.slug` is the only spreadsheet-facing Event identifier — Event UUIDs never appear in the template. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: closes the previously open import-template question.
- **D4 — Multi-invitee representation** — Decision: the `invitees` cell is a JSON array of objects carrying only `fullName`, `category`, and optional `label`. `category` accepts `ADULT` and `CHILD`, trimmed and case-insensitive, and is canonicalized to the uppercase literal; fuzzy synonyms such as `grownup`, `kid`, or `minor` are rejected. `displayOrder` is not accepted and is assigned server-side from array order starting at `0`. Duplicate invitee names are allowed and are not by themselves warnings, and at least one invitee is required per imported household. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: closes the previously open multi-invitee representation question; no name-uniqueness rule is introduced.
- **D5 — Event eligibility columns** — Decision: eligibility is expressed as `event:<Event.slug>` with the locked strict-boolean contract. `true` means the imported invitation is eligible for that event; `false` or blank means it is not. An unknown slug is a template/validation error. A known but **inactive** Event may still be parsed for an older template, but any row setting it to `true` produces the blocking row error `INACTIVE_EVENT`. Import never creates or modifies Event rows, and eligibility cardinality mirrors the existing single-invitation creation rules rather than adding a new minimum event-count rule. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: closes the previously open Event representation question.
- **D6 — Boolean, integer, and text normalization** — Decision: boolean fields (`allowPlusOne`, `event:<slug>`) accept only `true` and `false`, trimmed and case-insensitive, plus XLSX native boolean cells; `yes`/`no`, `y`/`n`, `1`/`0`, and `on`/`off` are rejected. A blank optional eligibility cell is `false`, while a blank `allowPlusOne` is a validation error. `maxAdditionalChildren` accepts a non-negative safe integer only (decimal integer text in CSV; integer numeric cell or decimal integer text in XLSX), rejecting negative, fractional, `NaN`-like, and scientific input. `displayName` is trimmed and must remain non-empty; blank `greetingName`, `label`, and `notes` become `null`. No new business-field length limit is invented where the normal create contract has none. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: closes the previously open boolean/enum normalization question.
- **D7 — Date/time normalization** — Decision: the spreadsheet column is named `rsvpDeadlineLocal`, deliberately not `rsvpDeadlineAt`, and is optional **text** in the exact format `YYYY-MM-DD HH:mm`, interpreted as `Asia/Jakarta` and normalized to a canonical UTC instant before domain creation. Blank means `null`. Ambiguous formats such as `16/01/2027` or `01/16/2027`, and Excel date-serial or date-formatted numeric cells, are rejected; workbook locale and timezone are never guessed. Preview shows both the source/local value and the canonical UTC value. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: closes the previously open date/time normalization question.
- **D8 — CSV and XLSX parsing policy** — Decision: CSV is UTF-8 (BOM allowed), comma-delimited, standard double-quote quoting with doubled-quote escaping, CRLF or LF, quoted multiline cells supported, first record is the header, completely blank records ignored, no delimiter auto-detection, and no legacy ANSI/codepage detection. Row numbers are record positions including the header, so the first data row is `2`. XLSX accepts `.xlsx` only, requires a visible worksheet named exactly `Invitations`, ignores other worksheets, rejects a missing or hidden target sheet, uses header row 1 and data row 2, and rejects formulas (cached values are not trusted and are never evaluated), merged cells within the target used range, Excel date-serial cells for `rsvpDeadlineLocal`, macros, and external-link following. The parser never makes network requests from workbook content. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: closes the previously open CSV/XLSX core parsing policy question.
- **D9 — Operational limits** — Decision: maximum upload size **5 MiB** and maximum **500** household data rows, counted after completely blank records are ignored and rejected before business parsing. XLSX parsing additionally uses bounded worksheet dimensions rather than trusting a declared range. These are Phase 9 operational limits, not permanent domain limits. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: the 500-row cap must be proven against real PostgreSQL before Phase 9 closes, and an explicit transaction timeout may be configured rather than relying on a default interactive transaction timeout.
- **D10 — Preview storage and lifetime** — Decision: validation persists a short-lived `GuestImportPreview` distinct from business invitation data and from `GuestImportBatch`. Uncommitted preview lifetime is **30 minutes**; the preview is bound to the OWNER who created it, and another admin session may not commit it. The preview stores the normalized rows needed to commit, so the browser never reconstructs or re-submits the household payload. Raw uploaded file bytes are never retained in the preview, in `GuestImportBatch`, in the database, or in long-lived temporary storage. **The model does not exist yet: Phase 9 requires a future Prisma migration to add it, and Slice 9A creates no migration.** Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: this closes the preview-storage half of the previously open Phase 9 blocking question.
- **D11 — Commit idempotency** — Decision: the preview is the idempotency boundary. A deterministic commit fingerprint is computed from the canonical `previewId` plus the sorted unique `includeRowNumbers` and `acknowledgedWarningRowNumbers`. The first successful commit atomically marks the preview committed, records the fingerprint, links the committed `GuestImportBatch`, and stores the minimal receipt. An exact replay returns the same committed result and creates no additional invitations; a different selection against an already committed preview returns `409 IMPORT_PREVIEW_ALREADY_COMMITTED`. An expired uncommitted preview returns `409 IMPORT_PREVIEW_EXPIRED` and is never silently regenerated. `admin-web` never automatically replays a commit; an uncertain outcome is recovered only by an explicit operator resubmission of the exact same selection. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: this closes the commit-idempotency half of the previously open Phase 9 blocking question; no batch-history endpoint is required in the MVP.
- **D12 — Commit selection and revalidation** — Decision: `includeRowNumbers` must be non-empty, must be unique, and may never include an `ERROR` row; `VALID_WITH_WARNINGS` rows are committable only when acknowledged, and acknowledgment never converts an error row into a valid row. Commit revalidates inside the transaction — preview not expired, preview owned by the current OWNER, selected rows still valid, current Event still existing and active when selected, canonical Invitation and Invitee business validation, and the duplicate state needed for a safe commit. If current state differs materially, commit performs **zero** business writes and returns `409 IMPORT_PREVIEW_STALE`. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: server-side validation is authoritative and client-side enforcement alone is never sufficient.
- **D13 — Import must not pre-create RSVP state** — Decision: commit creates no `RSVP`, `RSVPAttendee`, or `RSVPEventSelection` rows. A newly imported invitation follows the same lazy RSVP lifecycle as normal single-invitation creation, so no RSVP row exists before the first guest submission and that submission is a create with `expectedVersion = null`. Documentation wording such as "default RSVP state where used" is removed so it cannot be read as creating a `PENDING` RSVP row during import. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: import preserves the Phase 5D0 first-mutation `expectedVersion` contract and keeps the admin RSVP list to persisted RSVP rows only.
- **D14 — Import route placement** — Decision: the admin import route is `/invitations/import`, reached from an explicit Import CSV/XLSX action on `/invitations`. No top-level Imports navigation item is added, and the Invitations navigation section remains active on the import route. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: closes the previously open route-placement question and keeps import inside invitation management.
- **D15 — Upload security** — Decision: `.csv` and `.xlsx` are accepted; `.xls`, `.xlsm`, `.xlsb`, and arbitrary ZIP/Office payloads are rejected. Extension, declared media type where useful, and actual file signature/content are all validated, and none is trusted alone. CSV must decode as valid UTF-8, and the XLSX parser enforces the size cap, the row cap, bounded dimensions, and the no-formula, no-merge, no-macro, no-external-link rules. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: multipart handling, CSV parsing, and XLSX parsing dependencies are still gaps; Phase 9B must review maintenance, security, streaming/memory behavior, and OpenAPI compatibility before adding any dependency, and no package is locked by this slice.
- **D16 — Validation architecture** — Decision: import must not create an independent second set of invitation business rules. The parser owns file structure, cell decoding, import normalization, row location, and import-specific warning generation; the domain owns invitation business validation, invitee validation, event eligibility validity, credential creation rules, and database write invariants. Phase 9 implementation should extract and reuse the existing typed invitation-create domain/application logic. Date/phase: 2026-10-07, Phase 9 Slice 9A. Consequence: this is an architecture principle, not a slice plan; the concrete extraction point is an implementation decision.

### Invitation link regeneration retry/idempotency

- Status: **RESOLVED in Phase 8 Slice 8D0.** The endpoint requires `expectedTokenVersion`, rotates at most once per displayed state, and returns `409 CONFLICT` without rotating on a version mismatch. The client never auto-retries and treats an uncertain outcome as unknown; recovery is a plain re-read of `GET /api/admin/invitations/{id}/public-url`, which re-derives the currently valid link because derivation is deterministic. No idempotency key, no idempotency table, and no new column are added. The old credential stops resolving immediately after a committed rotation. See D12/D13 in the "Resolved by Phase 8 Slice 8D0" section above.
- Historical context: the open question was how to avoid a double rotation when the admin loses an ambiguous response. The deterministic derivation already present in the credential architecture made a stored idempotency key unnecessary.

### Import preview lifetime and idempotent commit semantics

- Question: How long does an import preview remain valid, and how is duplicate commit prevented if an admin retries?
- Why it matters: Preview storage, commit safety, and admin retry behavior depend on this.
- Impacted components/documents: API Contract, imports module, admin import UI.
- Blocking phase: Phase 9 before import implementation.
- Phase 4 impact: non-blocking.
- Possible choices: short-lived persisted preview; signed temporary preview token; idempotency key on commit.
- Status: **RESOLVED in Phase 9 Slice 9A.** The chosen mechanism is a short-lived persisted server-side `GuestImportPreview` rather than a signed temporary token or a separate idempotency table. An uncommitted preview lives 30 minutes, is bound to the OWNER who created it, and stores the normalized rows so commit never trusts a client-submitted reconstruction. The preview is the idempotency boundary: a deterministic fingerprint over the preview id plus the sorted unique selection and acknowledgment row numbers makes an exact replay return the original committed result, while a different selection against an already committed preview returns `409 IMPORT_PREVIEW_ALREADY_COMMITTED` and an expired preview returns `409 IMPORT_PREVIEW_EXPIRED`. `admin-web` never automatically retries a commit; recovery from an uncertain outcome is an explicit operator resubmission of the same selection. The model does not exist yet and Phase 9 requires a future Prisma migration to add it. See D10/D11 in "Resolved by Phase 9 Slice 9A" above.
- Historical context: the open question was whether preview state should be persisted at all or carried by a signed token, and whether commit needed its own idempotency key. Persisting the validated preview answered both at once, because the stored preview is both the commit source and the natural idempotency boundary; no separate key, column, or token is needed.
