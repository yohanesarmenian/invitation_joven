## OWNER setup

Open **Reports → Configure RSVP deadlines**. Set the wedding default in WIB when its actual date and time are approved. An explicit invitation deadline takes precedence. Clearing an explicit value makes the invitation inherit the wedding default, which can itself be unset. The settings panel identifies active exceptions and links to their invitation editors. Saving the wedding default leaves invitation rows intact.

The initial cutoff includes the exact saved instant. After it, first-time responses and persisted Pending rows are closed online. When late editing is enabled, existing Accepted and Declined responses remain editable within eligibility and composition limits. An optional final deadline bounds that late window. It requires the wedding default initial deadline and cannot precede it. A later invitation override retains its initial response window. A blank final deadline leaves late edits open until check-in. Check-in locks the household even after a correction to zero, and Guest Managers can handle authorized on-site RSVP and attendance through Reception.

## Catering operation

Open **Reports → Catering reports → LIVE**. Choose a session or all configured sessions and choose whether to include archived households. Counts cover households with an eligibility, RSVP selection, or check-in relationship in scope. Household and named-invitee totals deduplicate across sessions. Expected people per session include accepted RSVP counts and applicable Reception capacity adjustments. Actual people come from the corrected check-in aggregate. Walk-in arrivals are a subset of actual attendance.

Use **Freeze catering numbers** when the live scope is ready. Each version captures the OWNER, time, sessions, archive rules, and counts in PostgreSQL. **FROZEN** shows the captured data and **CHANGES** reconciles the original scope. A new session requires a fresh capture. The comparison flags causes that the history cannot verify.

If the browser loses the response, receives a server error, or cannot validate the receipt, use **Check Freeze Result** on the open Reports page. This resends the original freeze. It can return the stored receipt or complete the original operation if its version is still available. If another snapshot took that version, the server checks the original operation ID before confirming the conflict. **Review Latest Snapshot** opens the saved version and clears the conflict without a page reload. Creating another version requires a new click on **Freeze catering numbers**.

Export the frozen summary, frozen household/session detail, or current comparison as CSV. Frozen exports replay a specific version. Changes exports use the current comparison time.
