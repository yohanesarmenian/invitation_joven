# Event content administration

Owner-authorized scope: manage parking/rundown per existing Event, upload/replace/remove supporting images/PDFs, persist drafts, preview, explicitly publish or hide. This is a bounded content feature for this personal wedding, not a page builder or Event catalog editor.

## REA evidence and original decisions

The saved REA investigation observed rundown on the public preview (E3/E7) and records vendor documentation describing content management and event/session-specific presentation. No authenticated editor, upload validation, storage, or publication workflow was tested. The draft/published snapshot model, PostgreSQL storage, concurrency policy and authorization below are original implementation decisions, not assertions about Katsudoto internals. No vendor code, media or design assets are reused. Evidence: `D:/Projects/rea/.cache/katsudoto/analysis.md` and `evidence-projections.json`.

## Persistence and concurrency

Add `event_contents` (one row per Event, integer version, draft JSONB, nullable published JSONB and publication timestamp) and `event_content_assets` (Event FK, opaque UUID, normalized MIME, byte size, binary bytes, creation timestamp). Files are stored in PostgreSQL for this small personal application so DB backups include them; at most 8 files per Event and 5 MiB per file. No filesystem upload directory or object-storage credential is required.

All content/upload/delete/publish/hide mutations lock the Event row first, compare `expectedVersion` (0 for no content row), and increment version exactly once. Edits affect the draft only. Publish copies a validated draft into a separate snapshot; further saves leave that snapshot intact. Hide removes the published snapshot without deleting draft/files. There is no publication history/automatic rollback. Referenced files cannot be deleted while used by either draft or published snapshot; detach/save and update/hide publication first. Upload never publishes or automatically rewrites content.

No mutation is automatically retried. On timeout/malformed success, admin marks outcome uncertain and requires an explicit authoritative reload before further mutation. Version conflict also requires reload; local unsaved input is kept until the owner explicitly discards it. These transactions do not modify Invitation/RSVP/check-in/Event dates or eligibility.

## Contract

OWNER-only, independently enforced through shared admin session/role/CSRF/origin guards:

- `GET /api/admin/event-content/{eventId}`: draft, current snapshot, version, file metadata/reference flags.
- `PUT /api/admin/event-content/{eventId}`: `{ expectedVersion, content: { parking, rundown } }`.
- `POST /api/admin/event-content/{eventId}/publish` and `/hide`: `{ expectedVersion }`.
- `POST /api/admin/event-content/{eventId}/assets?expectedVersion=...`: exactly one multipart `file`.
- `GET /api/admin/event-content/{eventId}/assets/{assetId}`: authenticated binary preview/download.
- `DELETE /api/admin/event-content/{eventId}/assets/{assetId}`: `{ expectedVersion }`.

Public read-only endpoints:

- `GET /api/public/invitations/{publicCredential}/venue-content`: only published content of active eligible Events, no open-counter mutation.
- `GET /api/public/invitations/{publicCredential}/venue-assets/{assetId}`: requires active invitation, eligible active Event and reference from its current published snapshot. A guessed/old/draft/deleted/unpublished/ineligible file or invalid/rotated credential returns the generic invitation-unavailable 404.

Binary responses are no-store, nosniff, no-referrer and carry a restrictive sandbox CSP. PDFs are downloads, not embedded documents. Images accept PNG/JPEG/WebP only, verify extension/MIME/decoded format, reject animation/excessive pixel dimensions and decode/re-encode to a canonical PNG without source metadata. PDFs receive bounded signature/EOF checks and are attachment-only; no claim of PDF sanitization or malware scanning. Original filenames are not persisted or used as paths.

Parking: bounded title/instructions, optional image UUID + alt, optional PDF UUID, optional approved HTTPS Google Maps URL. Rundown: bounded title and <=30 items, each with ISO-offset startsAt, title and description; publish requires valid chronological instants and complete copy. Drafts may contain unfinished copy/times, but still enforce shape, lengths, UUIDs, file ownership and URL rules. Empty content cannot be published. Renderer uses Asia/Jakarta, plain-text escaping and the same preview/public components. File asset URLs are generated by each frontend; the API does not trust caller URLs.

The backend becomes the production source of truth. The prior JSON files remain development mock-preview material only; a backend error/unpublish must never fall back to an old published local file. Frontends consume generated OpenAPI types. Public media is proxied through a fixed same-origin invitation route; credentials never go to third-party origins or caches.

## Verification and migration boundary

Image decoder references: [sharp input constructor and limits](https://sharp.pixelplumbing.com/api-constructor/) and [output metadata behavior](https://sharp.pixelplumbing.com/api-output/). The actual normalization/metadata removal is also checked by PostgreSQL HTTP tests against uploaded bytes.

Migration is additive and is exercised on the isolated QA database only during implementation. Do not silently apply it to the configured development/production database. Prove save/reload persistence, published snapshot isolation, version races using real PostgreSQL, asset ownership/reference guards, OWNER/staff/unauth/CSRF/origin behavior and public credential/eligibility/revocation. Test browser save/upload/preview/publish/hide and uncertain-outcome recovery. Preserve original assets and opening flow; no commit without a separate request.
