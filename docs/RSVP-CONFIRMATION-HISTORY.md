# RSVP confirmation and change history — Phase 4B

Guests with no saved response (including a persisted PENDING row) see **Submit RSVP**. Saved ACCEPTED and DECLINED responses reopen as read-only **Attendance Confirmed** and **Unable to Attend** summaries. Accepted summaries show selected guests, quantities, selected events/counts, dietary requirements and the existing active check-in pass. Declined summaries show no pass.

**Edit RSVP** first reloads canonical state and server permissions. **Save Changes** submits that revision; **Cancel** restores the saved summary without a mutation. Reopening never implies edit mode. Internal versions remain in requests/responses for concurrency; ordinary public and Admin RSVP labels omit them.

An uncertain save or version conflict suspends the displayed pass and prevents another save until an explicit canonical reload. Recovery returns to the summary; further editing requires another explicit Edit. A request that finishes after a recovery read still cannot overwrite newer data: the invitation lock and expectedVersion check remain authoritative. No writes are retried automatically. GET remains available after the deadline/check-in; the server returns `canEdit` and nullable `editBlockedReason` (`DEADLINE_PASSED` or `CHECKED_IN`). These are presentation hints at read time; every mutation independently rechecks its restrictions under the invitation lock. Check-in takes precedence when both restrictions apply. OWNER overrides retain their existing deadline exception, with no exception to check-in locking.

QR wording before response: “Please confirm your attendance to receive your personal check-in QR code.” After acceptance: “Your check-in QR code is ready. Please present it at the reception desk.” Reception staff can assist when the QR cannot be read. Invitation credentials and check-in credentials remain separate.

## Atomic history and no-op semantics

Migration `20261111090000_rsvp_change_history` adds `rsvp_change_events`, its indexes, foreign keys and runtime immutability triggers. It does not update existing RSVP rows, credentials, passes or migration files, and does not backfill invented history. Existing responses display an explicit history-starts-now empty state until their next effective change.

The shared public/OWNER RSVP transaction validates credential/access, invitation state, deadline (public), expectedVersion, check-in lock and payload before changing anything. A genuine current-version no-op returns canonical state without incrementing the revision, rewriting child rows or adding history. Ordering, whitespace-normalized dietary notes, equivalent child quantities, and omitted versus explicit zero-count non-attending events do not create changes. A stale duplicate still returns the existing version conflict. Attribution and override reason are meaningful state: a later public submission clears current OWNER attribution as before and records that change, while preserving earlier OWNER history. Missing/inconsistent active-pass state is repaired through the normal lifecycle and recorded without storing QR material.

Each effective mutation appends one row in the same transaction, correlated by unique `(rsvp_id, revision)`. DB-default timestamp, action, actor category, optional authenticated Admin ID/role snapshot, before/after bounded RSVP JSON, human-readable field diff and override reason are stored. Initial guest submissions, guest updates and OWNER overrides are distinguishable. Notes/names are personal data: history is subject to the same protected backup/access policy as RSVP records. Public credentials, password hashes, session data and QR credentials are never selected for audit snapshots. A failed history insert rolls back the RSVP and pass lifecycle; failed requests do not append events.

Online database identities can SELECT/INSERT history. Migration revokes UPDATE/DELETE/TRUNCATE for `invitation_app`; triggers additionally reject them (including a parent RSVP delete cascade), even if a runtime identity accidentally has broader grants. Table-owner/migration maintenance identities can maintain data, as they inherently control the table/triggers. Never run the online API as the migration role. Maintenance/export/retention that would rewrite history requires a separately reviewed operator procedure. This PR performs none.

## Admin contract

The existing OWNER-protected `GET /api/admin/rsvps/{rsvpId}` returns top-level `history[]`, newest revision first. Entries expose `id`, `createdAt`, `action`, `actorCategory`, `actorRole`, `actorAdminUserId`, internal `revision`, optional reason and normalized `changes[]` (`field`, `label`, `before`, `after`). Raw before/after snapshots stay in the database. The detail timeline renders WIB timestamps and escaped text, without visible revision numbers. Unauthenticated requests receive 401; CHECKIN_STAFF receives 403. History has no public endpoint and is absent from public response projections and guest props.

Actor category/action/role snapshots are text, so future GUEST_MANAGER and on-site actions can be added deliberately without migrating an audit enum. This adds no new role, on-site RSVP, walk-in registration, approval flow or partial check-in. Phase 4C/4D must call the same locked transaction or preserve its atomic append invariant and access policy.

## Migration and release safety

Use the existing PostgreSQL backup and migration gate: `prisma migrate deploy` under the migrator before new API traffic. No reset, db push, destructive schema change or history backfill. Keep the migration table and new audit table on rollback; do not drop audit history. A rollback to an older API would stop recording subsequent changes, so prefer a forward correction and pause RSVP mutations if an audit-writing defect is found. The migration rollback decision is an operator gate, not an automatic procedure.

The local migration rehearsal applied the five existing migrations to a new disposable PostgreSQL 18 database, inserted a synthetic declined RSVP at revision 7, applied the new migration and compared the complete row checksum: identical before/after, zero invented history. A schema diff against the generated Prisma schema reported no differences. Production was not contacted or changed.

Verification includes real PostgreSQL audit insert failure/rollback, online-role immutability/cascade denial, no-op/stale concurrency, check-in restrictions, OWNER history attribution and public projection exclusion; browser confirmation/edit/cancel/reopen, conflict and lost-response recovery; mobile 320/375/412; and existing real guest-to-camera check-in/message journeys. Exact execution counts and hosted CI status belong in the PR report. Physical-device and assistive-technology acceptance and OWNER review remain separate from automated Chromium results.
